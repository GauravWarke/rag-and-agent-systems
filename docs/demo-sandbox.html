Permissioned Agent Sandbox

Pick a role, choose a tool call, and watch it move through the policy pipeline. Scope checks, rate limiting, risk classification, budget ceilings and the human approval gate all evaluate for real — including the rate limiter, which is stateful, so calling repeatedly will get you throttled.

What's real here: the entire policy engine. In the production service an LLM decides which tool to call; that choice is yours in this demo. Everything after it — the gating logic that is the actual point of the project — is the same logic as the repo, ported to run in your browser. Tool effects are simulated; the decisions about whether they'd run are not.

The pipeline, stage by stage

  1. Bind. The tool name is resolved against a registry that declares its required scope, risk tier and cost. A tool not in the registry cannot be called at all — the agent has no path to an unregistered capability.
  2. Scope. The caller's role is checked against the tool's required scope before execution. This is the difference between authorisation and after-the-fact auditing: a denied call never runs.
  3. Rate limit. A sliding 60-second window, 10 calls. Genuinely stateful in this demo — spam the button and you'll hit it. Limits sit at the tool boundary so a looping agent can't exhaust a downstream system.
  4. Risk tier. Registry-declared: low, medium, high, critical. Tier drives whether the next gates engage, so adding a tool means declaring its blast radius up front.
  5. Budget. Money-moving tools draw against a session ceiling. A call that would breach it is refused even when the caller's scope permits it — authorisation and spending authority are separate questions.
  6. Human gate. High and critical tiers suspend rather than execute. The agent gets a pending handle, not a result, and a person decides. This is the stage that makes the difference between an agent that can act and an agent that can act unsupervised.
  7. Execute & audit. Every outcome — allowed, denied, throttled, held, approved, rejected — is written to the hash-chained log. Denials are recorded as carefully as successes, since a refused call is exactly what an incident review needs to see.
